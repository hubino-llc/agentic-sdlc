AI-Native SDLC with Human-in-the-Loop (HITL) Governance

A software lifecycle in which role-specific AI agents do the work, people approve each step that matters, and the pipeline itself measures quality and keeps the evidence. This guide covers the whole path from brief to production: the phases, the gates, who does what, the documents produced, the standards applied, the guardrails that stop bad work, and the compliance evidence kept.

How it works in one minute

Agents do the work

Each task is done by a role-scoped agent (product manager, engineer, reviewer and so on). An agent can only read and write where its role allows, and cannot run Git.

People approve

Work stops at a gate until a member of the right team approves it. The person who made the work cannot approve it. Each approval is a comment on a GitHub issue that lists the documents to review.

The pipeline measures

Tests, coverage, security scans and dependency checks are run by the pipeline, not reported by the agent, so an agent cannot declare its own work good. Every step is written to a tamper-evident audit log.

The lifecycle

Orange markers are human gates. A dashed marker applies only in some cases. Work moves forward only when every earlier gate is approved.

  1. Pre-flightcharter, standards
    G0
  2. Researchstories, readiness
    G1
  3. Architecturecontracts, threats

  4. Planmilestones, order

2 · Build, story by story repeats for every user story, in order

  1. Implementtests first, per repo
  2. Integration testwhen 2+ repos change
  3. Reviewadversarial + checks
    G4
  4. Mergepull request

If review finds a problem, implement and review run again with the feedback (up to 3 rounds by default). A story that is still failing is blocked until a person releases it. Each story has its own branch, pull request, GitHub issue and merge approval. A setting switches this to one merge approval per milestone.

3 · Deliver to staging once per milestone, after its stories are merged

  1. Documentationhandoff, changelog
    G7
  2. Staging deployIaC, smoke tests
    G5
  3. Handovercumulative note
    GH

G7 applies only when the milestone changes the database schema. The next milestone starts only after the handover is approved.

4 · Release to production a separate, explicit run

  1. Release prepsecurity, SLOs, runbook
    G6G7PG8
  2. Production rolloutcanary, verification

G6 applies when residual security risks were recorded. G7P applies when any milestone in the release changes the schema. A release is blocked while high or critical vulnerabilities are open or overdue.

Gates: where a person decides

A gate opens a GitHub issue that lists the documents produced since the previous gate, with links. A member of the team mapped to an allowed role comments /approve or /reject <reason>. The pipeline checks team membership itself, and the author of the work cannot approve it.

How approval works

  • The run stops with a clear message and exits; a comment on the issue resumes it automatically in GitHub Actions.
  • Approving needs the right team, not just repository access.
  • A rejection halts the pipeline with the reason recorded.

Skipping a gate on purpose

When starting part-way from documents you already have, a gate can be waived with --skip-gates. A reason is required, it is recorded as approved by "waiver" with the operator's name, and it appears in the audit log and the compliance report.

Each role is an agent with its own prompt, model and permissions. Planning and architecture use the stronger reasoning model; story writing and documentation use the faster one; code, tests, deployment and review use the code and security models.

Standards applied

The standards are copied read-only into every workspace on every run, so an agent cannot water them down. The reviewer judges work against them, and a clear violation is a finding.

Engineering standards
  • Errors: no swallowed exceptions; a stable error code, correlation ID and safe message; no stack traces or SQL to clients.
  • Logging: structured JSON with a correlation ID; never secrets or personal data.
  • Observability: request rate, error rate and duration for every endpoint; live and ready health checks.
  • Reliability: SLOs with symptom-based alerts; graceful degradation; every deploy reversible.
  • APIs: the OpenAPI contract changes first and stays backward compatible.
  • Data: expand-and-contract migrations, each with a tested way back.
  • Quality: test first; coverage at least 85% on changed code; deterministic tests; decisions recorded as ADRs.
Release standards
  • Staging record for every milestone: smoke tests and rollback, with unverified items stated.
  • Release readiness for every release: SLOs, observability, runbook, rollback plan, numeric rollback criteria, release notes, migration rollback.
  • Security record: residual risks with owners; S1 and S2 findings are fixed, never accepted.
  • Rollout: canary first, never 0% to 100%; rollback rehearsed on staging; a tag in every repo and the previous tag as the rollback target.
Secure coding standard
  • Validate input at the edge; parameterised queries; encode output for its context.
  • No secrets in code, logs, URLs or bundles; current cryptography only.
  • Authorisation checked on the server for every request; least privilege; rate limits.
  • Pinned dependencies; none with known high or critical vulnerabilities or a licence outside the allow list.
  • Findings are fixed or formally accepted, never silenced.
Mobile standards (React Native)
  • Credentials only in the platform keystore, never in plain storage or logs.
  • TLS everywhere; minimum permissions requested when needed; deep links validated.
  • Loading, empty, error and offline states on every screen; accessibility labels and large-text support.
  • Behaviour verified on one platform only is stated as such.

Guardrails: what stops bad work

Controls sit at six levels. The ones the pipeline measures itself fail closed: a missing report counts as a failure.

LevelControlHow it is enforced
1 · Quality gatesTests pass; coverage at least 85%; no high-severity scan finding; reviewer verdict PASS; reviewer independent of the buildersThe pipeline runs each repo's test, coverage and scan commands and reads the reports. A failure sends the story back with the feedback.
2 · Human gatesEleven approval gates, in orderA GitHub issue per gate; team membership checked through the API; a phase cannot start with an earlier gate open; the author cannot approve.
3 · Agent sandboxWorkspace only; per-role read and write limits; protected filesPaths are resolved and checked; .. and symlinks that escape are rejected; reviewers are not given a write tool.
4 · Command executionOff by default; allowlisted commands onlyNo shell operators; a minimal environment with no keys or tokens; timeouts and output caps; optional Docker with no network.
5 · Git safetyBranch per story; no secrets committed; merges only after approvalThe pipeline, not the agent, commits, pushes and merges; secret-looking files are refused; test output is kept out of commits.
6 · Audit and integrityTamper-evident log; sealed state; required sections presentEach audit event carries the hash of the previous one; the state file is checksummed; incomplete deliverables send a phase back.

Limits on cost and loops: a cap on rework rounds, on tool turns per task, and on output per turn; a check that the scanning tools are installed before work starts; and a blocked story stays blocked until a person releases it.

How a vulnerability is handled

  1. Scan finds it
  2. →
  3. Registered with owner and due date
  4. →
  5. Ticket opened (high and critical)
  6. →
  7. Story sent back for rework
  8. →
  9. Later scan no longer reports it
  10. →
  11. Marked fixed and verified; ticket closed

If there is no fix, a person can accept the risk with a written reason. It is recorded in the register and the audit log, and the release then goes through the security acceptance gate (G6).

Evidence files

  • quality-gates.jsonl review history
  • vulnerabilities.json register
  • inventory.json and reports/…/sbom.json
  • deployments.jsonl promotions
  • report-<date>.md and evidence-index.json

Retention

Evidence is committed to the state branch at every gate and published as a workflow artifact kept for a configurable number of days (365 by default). The index lists every file with its SHA-256 and is sealed with an HMAC when an integrity key is set.

This evidence supports an audit. It does not by itself certify compliance with any named framework.

A BRD is an input, not a skip: import it as docs/brd.md and the research phase reads it. Imported files are checked before anything is written; if one is missing or invalid the run stops and lists exactly what is wrong.

Run it

The recommended way is GitHub Actions: gate approvals are comments on the issues, and a comment resumes the run. The same runner works from the command line.

One-time setup
  • A control repository holding the playbook, plus one repository per backend and client.
  • A GitHub organization with teams matching the approver roles, and a GitHub App for the pipeline.
  • Secrets for the model API key, the App key and an integrity key; a variable that allows command execution.
  • Install the scanning tools where it runs: a coverage tool, Bandit, Semgrep, pip-audit and a CycloneDX generator, plus Node for the web and mobile repos.
Before the first run
  • Write the brief with its seven sections (goal, users, scope, constraints, repositories, non-functional requirements, compliance).
  • Validate the configuration.
  • Do a dry run without the live flag, which is free.
Start a run in GitHub Actions
# start (or restart after a gate; comments on a gate issue also resume it)
gh workflow run sdlc-run.yml -f live=true -f platforms=web

# start part-way from imported documents
gh workflow run sdlc-run.yml -f live=true -f import_dir=imports/ -f start_at=architecture

# ship staged milestones to production
gh workflow run sdlc-run.yml -f live=true -f release=true
Or from the command line
python scripts/validate_playbook.py                 # check the configuration
python scripts/sdlc_runner.py                       # free simulation, prompts at each gate
python scripts/sdlc_runner.py --live --git --github-approvals --allow-commands --data-dir sdlc-data
python scripts/sdlc_runner.py --status              # progress, imports, waivers
python scripts/sdlc_runner.py --unblock M1.2        # give a blocked story another round
python scripts/sdlc_runner.py --compliance-report   # write the compliance report now
python scripts/sdlc_runner.py --accept-risk KEY --reason "..."   # accept a finding with no fix
python scripts/sdlc_runner.py --verify              # check the audit chain and state
